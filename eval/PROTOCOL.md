# 評価プロトコル v3(検査表世代)

編成比較の公式評価はこのドキュメントに従う。ここに書いていない手順で出した数字は参考値であり、公式表・記事には載せない。

## 0. 世代管理

| 世代 | 方式 | 位置づけ |
|---|---|---|
| v1 | diff-only judge(`scripts/judge.ts`) | 廃止。diff外のコードを検証できない |
| v2 | repo-verified 感覚6軸(`v3-assets/judge-protocol-v2-header.txt`) | 参考のみ。overall が閾値型で品質差を圧縮することを実測(混成/単独が実欠陥差ありで同点 5.67) |
| **v3** | **repo-verified 検査表 + 欠陥プロファイル(本書)** | **公式** |

## 1. 評価対象

1 run = (編成 runtime.yaml, ワークフロー, 題材タスク) の実行。評価に使う成果物は次の3つ。

- 完成 worktree(実装コミット済み)
- `.takt/runs/<slug>/` のレポート・ログ(周回構造の読み取りに使う)
- プロバイダ側の呼び出しログ(トークン計測に使う)

## 2. 測定は3系統。合成しない

### A. 実装品質 — 検査表(絶対評価)

- 検査表 = 共通節(`eval/rubrics/_common.md`: AP=AIアンチパターン / AR=アーキテクチャ / T=テスト)+ 題材別節(F=機能の正しさと堅牢性)。
- 判定基準の正本は **TAKT リポジトリ自身の builtin facet**(`builtins/ja/facets/policies/ai-antipattern.md`, `builtins/ja/facets/knowledge/architecture.md`)。judge は採点前にこの2ファイルを読む。自作基準で上書きしない。
- 各項目は 3値: 2=正しく堅牢 / 1=不完全・場当たり的 / 0=なし・壊れている。テストの有無は AP/AR/F の判定に含めない(T節で独立に判定)。
- 全項目に根拠 file:line 必須。推測判定は禁止。見つけられなければ 0。

### B. 欠陥プロファイル — 序列を決める正本

素点合計は均等配点で実害を平すため、**順位付けには使わない**。順位は落ちた項目の分類と辞書式比較で決める。

- 分類は題材検査表の作成時に項目へ固定する(採点後に決めない):
  - `correctness`(正しさ破壊): 現実的な入力で誤った結果を出す
  - `safety`(安全余裕): 敵対的・稀な条件でのみ問題になる
  - `discipline`(規律): 実行時挙動に影響しない作法(AP節は原則ここ)
  - `design`(設計): 構造の質(AR節は原則ここ)
- 3採点平均で項目を3値化: 平均 <0.5 = 欠落 / <1.5 = 不完全 / それ以外 = 成立。
- 比較は辞書式: correctness → safety → discipline → design の順に(欠落数, 不完全数)を比較し、最初に差が出た階層で決着。重み係数は導入しない。

### C. 効率 — 品質と合成しない別表

- **codex トークン**: codex CLI セッション JSONL の `token_count` を run 時間帯で合算。非キャッシュ入力と出力を報告(キャッシュ済み入力は別掲)。
- **呼び出し数**: 同セッション群の API 呼び出し数。
- **所要時間**: run 開始〜COMPLETE。
- **ステップ単価**: ループ回数差を補正するため、implement / review 1周 / fix 1周 あたりのトークンを役割別に報告する。分母の反復回数は `.takt/runs/<slug>/` のレポート系列から数える。

## 3. 採点プロトコル

- judge モデル: **codex gpt-5.6-sol, reasoning high**。read-only サンドボックスで**成果物 worktree の中で**実行する(repo-verified。diff だけを見せることは禁止)。
- **独立 n=3**。同一プロンプト、採点間で情報を共有しない。
- 実行は `eval/scripts/judge.sh <worktree> <題材rubric> <出力prefix> [n]`。
- 集計は `eval/scripts/aggregate.mjs <題材rubric> <label>=<logprefix> ...`。項目平均・節合計・欠陥プロファイル・辞書式判定まで機械的に出す。

## 4. 題材別検査表の作り方

- F節の項目は**発注書(task.md)の要求と、実測で見つかった欠陥クラス**から起こす。実装を見てから項目を足すのは可(発見の言語化)だが、**一度どれかの run を採点したら以後凍結**。凍結後の変更は全対象の再採点を要する。
- 各項目に classification ブロック(rubric 内の ```json classification フェンス)で分類を付与する。
- 項目は「実装のどの性質が成立しているか」を問う形にする。特定の実装手段(ライブラリ名など)を正解に書かない。

## 5. 報告様式

公式報告は次の順で並べる。

1. 辞書式判定(どの階層で決着したか+落ちた項目名)
2. 検査表の節合計(参考値と明記)
3. 効率表(トークン・時間・ステップ単価)
4. v2 感覚judge の値を載せる場合は「参考(圧縮バイアスあり)」と明記

採点ログは `eval/results/<題材>/<編成ラベル>-r<N>.log` に保存する。公式数字は必ずこのログから再集計できること。
